# 1. Prolegomena.
## 1.1. ARM vs x86. RISC & CISC.

In this section, before presting advanced stuff about ARM64 disassembly, we are going to make sense of some introductorial notions about processors, assembly and ARM64.

<br>

A CPU, as a [DTM](https://gsanmi1.github.io/posts/2026/01/11/PvsNP/), can be understood as an ordered-step structure. The state of the CPU is the snapshot of the components (Registers, RAM, Flags, etc) and the step between states is induced by what we call an *instruction*. A set of instructions that allows a CPU to depart from the initial state to a HALT state through the manipulation of his components is what we call an *architecture* like ARM64, the subject of this course.

<br>

Registers are ultra-fast storage units, in contrast with volatile memory or flash memory, registers don't have address, they live inside the procesor and the instructions refers to registers by his own name. 

Registers are used to store data to allow the ALU to operate on it. (For reasons of optimization and data recursion) it is a more efficient to translate data from volatile memory to some register once and operate with it several times than call it each time is required.

<br>

ARM64 is a RISC (load/store) calculation instructions never access memory, instead, it operate with registers, and memory is read or written only via explicit instructions.

In x86-64, some ```add``` operation may need only one step:

```
add rax, [rbp]
```

Since the procesor loads the data in ```rax``` at the time it performes the operation. The same operation in ```ARM64``` needs two steps, once to load and another to operate:

```
ldr x9, [x1]
add x0, x0, x9
```

Hence, only load/store instructions (```LDR```, ```STR```, ```LDP```, ```STP```, etc) access memory and arithmetic-logic instructions operate only on registers or immediate values, this is the most distinguisfully part from x86-64 (with some minor exceptions).

<br>

## 1.2. Register nomenclature.

The rough idea behind RISC is to make instructions simpler so as to make room for more registers. AARCH64 (what we are studying) has a lot of registers. Thirty two integer registers and thirty two floating point registers.

Specifically, 32 integer registers and 32 floating point registers. Although certain registers are reserved for specific purpouses, the general rule is:

$$\text{register "}rn \text{"} \to \begin{cases}r \in [A-Z]  & = \text{register type} \\ n \in \mathbb{Z}^+: & =  \text{number} \end{cases}$$

The kind of register is specified by a letter. Which register within a given type is specified by a number.

<br>

| Letter | Type |
|-|-|
| x	| 64 bit integer or pointer| 
| w | 32 bit or smaller integer|
| d | 64 bit floats (doubles)|
| s | 32 bit floats|

<br>

Hence, in our code we could find ```char``` or ```char *```, this, is a ```C``` directive to declare some fixed-size integer/pointer variable and in the disassembly we would see ```w1``` (to char) or ```x6``` (to pointer) or something of the kind. Is important to mention that register doesn't have to be declare, they just exists even when they are empty. Rigurously, they are fisically hollow deposits in the processor.

## 1.3. Instructions.

### 1.3.1. Instructions information: Mnemonics and Op-codes.

Every AARCH64 instruction is 4 bytes wide. 

Everything the CPU needs to know about what the instruction is and what variation it might be plus what data it will use will be found in those 4 bytes. Every instruction is specified by a mnemonic consisting of some letters which the assembler converts into numeric op-codes.

Essentially, from the processor perspective, an instruction is simply a number of 32 bits, in fact, an assembled program is a strings of numbers in memory. In this sense, each number acts as formulary with information, some numbers says what to do and some numbers indicates with what do what has to be done. The bytes that identifies the operation is what we call *op-code*:

```
                  op-code     extra    Rm     extra     Rn      Rd
sub x3, x5, x7    11001011     000    00111   000000   00101   00011
add x3, x5, x7    10001011     000    00111   000000   00101   00011
                   ^  only one byte of difference
```

In some cases, some instructions doesn't have his own op-code, for example ```mov``` is translated as a sequence of ```orr``` and ```xzr```. This way, processor understand how to make some translations, for example:

```
sub    x0, x0, x1   -->     x0 = x0 - x1
mov    x0, x1       -->     x0 = 0 OR x1 
```

<br>

### 1.3.2. Mixing Registers.

Different register types cannot be part of the same instruction, for example, given: ```
mov    w0, 10```, then you could do:

```
add x1, x0, x1 //All registers are 64 bytes type.
```

But, even if the operation makes sense, ```add x0, w1, x0``` is not allowed since you are mixing different type registers in the same instruction.

Putting a smaller-than-64-bit value into an integer register zeros out the higher order bits (ignoring the sign bit). So, you can safely view the ```x``` register when a value was placed into its corresponding ```w``` register.

<br>

### 1.3.3. Memory Instructions.

The [AARCH64 ISA](https://support.arm.com/documentation/102374/0103/Overview) permits operations to be performed only on data in registers (with few minors exceptions). Thus, we are interested in be familiar with those families of instructions whose purpouse is to load data into memory.

Two obvious instruction families are those for **transferring data from RAM to register(s)** and those for **transferring data from register(s) to RAM**.

Both loading and storing instructions must specify:

- The registers involved

- The address in RAM involved (always held in an ```x``` register)

<br>

#### 1.3.3.1. Loading. LDR.

Loading has the general form of: ```ldr    rn, [xm]```

This is like:

```
type * ptr = <ADDR>;
type var;

var = *ptr;
```

<br>

#### 1.3.3.2. Storing. STR.

Storing has the general form of: ```str    rn, [xm]```

This is like:

```
type * ptr = <ADDR>;
type var;

*ptr = var;
```

The analogies are not exact but close. 

Pairs of registers can also be stored and loaded with the stp and ldp op codes.  Post increment and decrement of the pointer is also supported. Pre increment and decrement of the pointer is also supported.
